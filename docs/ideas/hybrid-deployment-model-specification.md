# Hybrid Deployment Model Feature Specification

## 1. Purpose
The Hybrid Deployment Model allows users to choose between two target environments for deploying applications generated by BuildPad: either within the user's private cloud tenancy (self-hosted/bring-your-own-cloud) or managed directly on BuildPad's infrastructure. This provides flexibility for organizations with strict compliance, data residency, or security constraints while retaining the option for fully managed cloud hosting.

## 2. Users and Jobs
- **Cloud Platform Engineers / DevOps Managers:** Connect and configure their private cloud tenancies so that generated applications can be automatically provisioned within their corporate governance and perimeter boundaries.
- **Application Developers / Product Builders:** Select the deployment target (BuildPad Cloud vs. Customer Cloud Tenancy) during the project setup or deployment phase without modifying application codebase architecture.
- **Compliance and Security Officers:** Audit deployment configurations to ensure enterprise applications and associated datastores remain entirely within internal cloud accounts.

## 3. Functional Requirements
- **FR1:** The system shall present a deployment target selector allowing users to choose between "BuildPad Hosted" and "Customer Cloud Tenancy" during project configuration or deployment setup.
- **FR2:** When "Customer Cloud Tenancy" is selected, the system shall provide integration connectors and authentication flows (e.g., IAM roles, service principals, API tokens) to establish secure deployment access to the user's cloud account.
- **FR3:** The system shall validate connection credentials and permissions against the target cloud tenancy before allowing build or deployment pipelines to trigger.
- **FR4:** The system shall package generated application artifacts (containers, configuration manifests, and infrastructure-as-code scripts) tailored to the selected target environment.
- **FR5:** For "BuildPad Hosted" deployments, the system shall automate provisioning on BuildPad-managed infrastructure without requiring external credential setup.

## 4. Flows
### Flow 1: Selecting and Configuring a Hybrid Deployment Target
1. User navigates to the Project Deployment settings within BuildPad.
2. User selects the deployment mode: `BuildPad Hosted` or `Customer Cloud Tenancy`.
3. If `Customer Cloud Tenancy` is selected:
   a. User inputs cloud provider details (e.g., AWS, GCP, Azure).
   b. User provides requisite authentication credentials or executes an automated provisioning script/CloudFormation/Terraform template in their account.
4. System verifies connection status via a test health-check call.
5. System saves the deployment configuration and transitions the project status to `Ready for Deployment`.

### Flow 2: Deploying to the Selected Target
1. User triggers a deployment action from the BuildPad dashboard or via CI/CD webhook.
2. BuildPad compiles and packages the application.
3. BuildPad evaluates the active deployment target:
   - If `BuildPad Hosted`, artifacts are pushed to the internal BuildPad cluster.
   - If `Customer Cloud Tenancy`, artifacts and IaC templates are deployed directly into the customer's authenticated cloud environment.
4. System reports deployment progress, logs, and final endpoint URL back to the BuildPad UI.

## 5. States
- `Not Configured`: Default state before a deployment target is chosen or authenticated.
- `Validating`: State while testing credentials and permissions against the customer cloud account.
- `Connected`: Target is successfully verified and ready to receive builds.
- `Deployment In Progress`: Build artifacts are actively being transferred and provisioned.
- `Deployed`: Application is successfully running on the target infrastructure.
- `Error / Failed`: Credential check, build transfer, or provisioning failed; displays diagnostic messages.

## 6. Edge Cases
- **Expired or Revoked Cloud Credentials:** If the connection to the customer cloud tenancy fails mid-deployment, the system must catch authorization exceptions, flag the deployment state as `Error`, and prompt the user to re-authenticate without exposing raw secrets in plain text logs.
- **Partial Infrastructure Provisioning:** If provisioning fails halfway in the customer cloud tenancy, the system should provide rollback instructions or automated cleanup scripts where supported by the cloud provider's IaC engine.
- **Network Partitioning / Timeout:** Handle transient network dropouts during artifact transfer to external cloud tenancies with automatic retry logic (up to 3 attempts with exponential backoff).

## 7. Data Considerations
- **Secret Management:** Customer cloud credentials, access keys, and tokens must be encrypted at rest using industry-standard KMS (Key Management Service) and never logged in plain text.
- **Data Residency:** When `Customer Cloud Tenancy` is selected, all application runtime data, logs, and persistent storage volumes must reside strictly within the user's cloud boundaries.
- **Metadata Retention:** BuildPad retains only deployment metadata (status history, build timestamps, and target type) necessary for dashboard visibility.

## 8. Security and Privacy
- **Principle of Least Privilege:** Integration documentation and automated onboarding templates must request only the exact IAM permissions required for deploying and managing the generated application.
- **Secure Communication:** All communication channels between BuildPad's control plane and the customer cloud tenancy must use TLS 1.3 encryption.
- **Audit Logging:** All deployment actions initiated from BuildPad into a customer tenancy should be traceable via both BuildPad audit logs and the customer's native cloud audit trails (e.g., AWS CloudTrail).

## 9. Accessibility
- The deployment target selection interface and connection status indicators must comply with WCAG 2.1 AA standards, supporting full keyboard navigation, explicit ARIA labels for connection states, and high-contrast indicators for success/error statuses.

## 10. Acceptance Criteria
- [ ] Users can successfully select between `BuildPad Hosted` and `Customer Cloud Tenancy` deployment models.
- [ ] The system validates customer cloud credentials successfully and blocks deployment if permissions are insufficient.
- [ ] Generated applications successfully provision and run inside a verified customer cloud account.
- [ ] Generated applications successfully provision and run inside BuildPad's managed infrastructure when selected.
- [ ] Detailed error messages and logs are surfaced when deployment credentials fail or timeouts occur.

## 11. Non-Goals
- Providing a general-purpose multi-cloud management platform or Kubernetes cluster manager outside of the specific applications generated by BuildPad.
- Managing multi-region active-active database replication natively within the initial release of the hybrid deployment model.
